# PE_EXP

## Запуск

Из корня проекта, в окружении с зависимостями из `PE_EXP/requirements.txt`:

```powershell
python -B -u PE_EXP/run.py
```

По умолчанию используется `cuda:0`. Обучение запускается в текущем терминале;
оставьте его открытым. Скрипт удерживает Windows от автоматического сна, пока
работает, и восстанавливает прежнее состояние при выходе. Закрытие крышки,
ручной сон и отключение питания этим не отменяются.

Повторная **та же команда** продолжает сохранённый запуск. Checkpoint записывается
после каждой validation и при переходах CL; после аварии незаписанные шаги
повторяются. Завершённые тестовые точки повторно не считаются.

```powershell
python -B PE_EXP/run.py --dry-run
python -B -u PE_EXP/run.py --device cuda:1
python -B PE_EXP/verify.py
```

Первый вызов проверяет матрицу, модели и допустимость длин без обучения.
`verify.py` — короткие CPU-проверки протокола, включая восстановление параметров
и optimizer state. В тестах логики остановки accuracy подменяется; эти результаты
не относятся к эксперименту. Их артефакты находятся в `results/verification`.

Для отдельной задачи используйте отдельный каталог результатов:

```powershell
python -B -u PE_EXP/run.py --tasks sorting --output PE_EXP/results/sorting_only
```

Конфигурация: `experiment.json`. При изменении конфигурации, списка задач или
исходного кода нужен новый `--output` внутри `PE_EXP/results`. Проверка manifest
предотвращает незаметное смешивание несовместимых запусков.

## Матрица и обучение

Всего **408 моделей**: 15 задач из `POSITIONAL_TASK_DEFAULTS` в
`tasks/positional_lab.py`, `kv_retrieval`, `sorting`; 12 энкодингов;
seeds 1337 и 2026. Отдельной папки `pe_experiments` в текущем checkout нет:
задачи взяты из реестра positional lab, архитектура и seeds — из `pe_lab.yaml`.
В удалённой EVE-PE каталог `PE_experiments` есть: его конфиги также учтены.

Энкодинги: `nope`, `wpe`, `sinusoidal`, `rope`, `fope`, `alibi`,
`relative_bias`, `cope`, `cape`, `rope+alibi`, `rope+relative_bias`,
`wpe+relative_bias`. Это все отдельные механизмы из `SLOTS` и комбинации
из `PE_experiments/configs` удалённой EVE-PE. `nope_relative_bias.py` там
задаёт тот же `relative_bias`, поэтому дублирующий запуск не создаётся.

В `runtime/` лежит неизменённая копия необходимых модулей текущего проекта
(происхождение — `runtime/ORIGIN.md`). Скрипт использует именно её: папка
PE_EXP самодостаточна и работает также в удалённой ветке со старой структурой.
Зависимости Python перечислены в `PE_EXP/requirements.txt`.

Архитектура: 4 слоя, 4 головы, embedding 128, context 256, dropout 0, bias false.
Для WPE таблица позиций сразу выделяется под весь тестовый контекст;
позиции вне обучающего диапазона не получают обучающих сигналов от ответов.
Специальные параметры FoPE/CoPE и остальных PE сохраняют defaults модели.

Данные потоковые, поэтому **1 эпоха = `steps_per_epoch` optimizer steps**,
по умолчанию 1. Один step содержит 256 примеров. Это не проход по конечному
датасету. Validation выполняется каждые 250 эпох на всех 1000 фиксированных
примерах, без случайного пересэмплирования minibatches. Число эпох, шагов и
текущая стадия сохраняются отдельно.

AdamW: LR 1e-4, линейный warmup 100 steps, затем постоянный LR; weight decay
0.1, betas 0.9/0.95, clipping 1.0. Постоянный LR после warmup позволяет
продолжать CL без неизвестного заранее горизонта cosine decay.

Логический batch 256 разбит на microbatches по 8, validation/test — по 8.
Loss при accumulation взвешивается по числу ответных токенов: это эквивалент
loss полного batch даже для sorting с разной длиной ответа. При CUDA OOM
microbatch уменьшается вдвое; тот же batch пересчитывается до optimizer step.
Логический batch и число эпох сохраняются. Если не помещается даже один
пример или возникает другая ошибка, ошибка записывается, остальные задачи
продолжаются. На RTX 2070 используется FP16 с GradScaler, на GPU с нативным
BF16 — BF16, на CPU — FP32. Состояние GradScaler сохраняется в checkpoint.
При переполнении градиентов FP16 тот же batch повторяется с меньшим scale;
после 16 неудачных попыток запуск модели завершается с ошибкой.

Результаты по умолчанию записываются в `PE_EXP/results/rtx2070`. Старые результаты
в `results/full` остаются отдельно: после изменения precision/code их manifest
несовместим с новым запуском. Проверки FP16, переполнения и resume выполняются
в `verify.py`, если доступна CUDA. Потребление памяти именно на RTX 2070 не измерено.

Для lab-задач:

1. Обучение до `val acc == 1.0` либо 6 последовательных validation без строго
   большего accuracy. Первая validation задаёт baseline и не считается stale.
2. После остановки всех энкодингов и обоих seeds выбирается максимальное число
   эпох **по всей задаче**.
3. Каждая отставшая модель продолжает обучение из своего последнего состояния
   до этого максимума, с сохранением optimizer/RNG, без early stopping.
4. Тестируется финальная модель после выравнивания, а не лучший ранний checkpoint.

KV и sorting:

- `i=1..24`: ровно 500 эпох на диапазоне размеров **[2, 2i] включительно**.
  Для генераторов проекта это передаётся как tuple `(2, 2i+1)`.
  Даже accuracy 1.0 не сокращает эти стадии.
- `i=25`: диапазон [2, 50], до `val acc == 1.0`, без patience и верхнего лимита.
  Первые 24 стадии суммарно дают 12000 эпох.
- После достижения цели всеми моделями — то же выравнивание до максимального
  числа эпох задачи; дополнительные эпохи проходят на [2, 50]. Повторно
  требовать 100% после выравнивания нельзя без изменения общего бюджета:
  итоговая accuracy может отличаться от accuracy при первой остановке.
- KV и sorting чередуются по раундам; внутри раунда каждый ещё обучающийся
  энкодинг/seed получает 250 эпох. Недостижение цели одной моделью не мешает
  продвижению остальных моделей и второй CL-задачи. Lab-задачи выполняются раньше.

**Финальный CL может идти неограниченно долго**, если модель не достигает 100%:
так буквально реализовано условие «до победного». Завершение за время обеда
не гарантируется. Полный запуск при подготовке скрипта не выполнялся.

## ID/OOD и acc(L)

Для каждого seed заранее сохраняются общие для всех энкодингов данные:
validation каждой стадии и тест каждой длины. Все эти множества не пересекаются
по SHA-256 prompt, а training отвергает любой prompt из них. Генераторы задач
и ответы не изменяются. Начальные train RNG совпадают у разных энкодингов;
при одинаковом числе шагов они видят одинаковый поток примеров.

На **каждую точку каждой модели — ровно 2000 уникальных тестовых примеров**,
включая последний неполный minibatch. Accuracy — число полностью правильных
ответов / 2000. Для sorting нужен правильный порядок всего ответа.

Exact match вычисляется параллельно по teacher-forced logits. Для причинной
модели это тот же критерий, что и полное совпадение greedy autoregressive
ответа заданной длины: до первой ошибки префиксы совпадают, а после первой
ошибки exact match уже равен нулю. Token accuracy и sampling generation
не используются.

| Задачи | Определение L | ID | OOD |
|---|---|---|---|
| 15 lab-задач | длина prompt в токенах | все целые 16..32 | 40..256 с шагом 8 |
| KV | число пар | все целые 2..50 | все целые 51..63 |
| sorting | число элементов | все целые 2..50 | все целые 51..128 |

KV занимает `4L+4` входных токена, sorting — `2L` с учётом answer prefix;
поэтому точки помещаются в context 256. Словари KV и sorting: 80 значений,
у KV также 80 ключей без дубликатов. У sorting дубликаты разрешены.

Здесь OOD — **экстраполяция длины**. Остальные параметры lab-генераторов
сохраняют defaults: distance_range [4,8], correlation +1 и т.д. Дополнительный
correlation flip или отдельный sweep расстояний не подмешивается в acc(L).
Имена вроде `context_correlation_flip` сами по себе не включают смену
correlation в исходном классе.

Исходный `PositionalLabTask._content_retrieval` может перезаписать правильную
пару distractor-ом; для некоторых вариантов ответы становятся неоднозначными.
Это ограничивает достижимую accuracy. Оно сохранено намеренно, чтобы не менять
поставленные задачи или файлы проекта; lab patience позволяет завершить такие
запуски.

## Результаты

Всё записывается в `PE_EXP/results/full` (или указанный `--output`):

- `manifest.json` — конфигурация, список задач, хеши исходников;
- `environment.json`, `console.log` — окружение и общий журнал;
- `<task>/data_seed=<seed>.pt` — validation/test и множество исключений training;
- `<task>/seed=<seed>/<encoding>/last.pt` — модель, optimizer, RNG, стадия,
  счётчик patience, discovery/alignment status;
- там же `status.json`, `metrics.jsonl`, `acc_L.json`;
- `<task>/alignment.json` — общий бюджет задачи;
- `acc_L.csv` — все точки отдельно по seed;
- `<task>/acc_L.png` — кривые, усреднённые по seeds, с границей ID;
- `failures.json`, `completion.json` — ошибки и итоговый статус.

Checkpoint заменяется атомарно. После аварии в JSONL могут остаться записи
о шагах, повторённых с последнего checkpoint; источником состояния является
`last.pt`. Финальные acc(L) не дублируются. Итоговый код выхода 0 означает
успех всех выбранных задач, 1 — ошибки. При Ctrl+C сохраняются уже записанные
checkpoint и тестовые точки; повторный запуск продолжит работу.

`PE_EXP/.gitignore` исключает всю папку `results`; корневой `.gitignore` и
остальные файлы проекта не изменены. Bytecode отключён, runtime-кеши и
временные файлы направлены внутрь результатов. Два процесса не могут
одновременно писать в один каталог результатов благодаря OS file lock.
